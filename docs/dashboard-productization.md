## 3. 页面跳转

### 3.1 方案：page_link 加 query params

`st.page_link(page, query_params=...)` 负责跳转，query params 负责带上下文。

| 参数 | 用途 | 谁读 |
|---|---|---|
| `date`、`conf` | 日期、置信度 | `app.py`（侧边栏） |
| `from` | 从哪条限额规则跳来 | 目标页顶部的一行说明 |
| `inst` / `ind` | 要高亮的个股 / 行业，逗号分隔 | 敞口页 |
| `metric` | 归因指标 | 归因页的单选 |
| `scenario` | 情景 | 压测页的下钻下拉框 |

**目标由规则的 metric 推出，不按 rule_id 写死**（`tf.limit_target`）。新增一条规则不用改看板。

| metric | 跳到 | 带什么 |
|---|---|---|
| `concentration_instrument` / `concentration_industry` | 敞口页 | scope 指名的成员；`*` 时取 `detail.members`（超过预警线的成员，从大到小）；没有成员超线时取占比最大的那个（检查值就来自它） |
| `var_hs_99`、`es_hs_95`、`var_param_xx` | 归因页 | 指标和置信度从 metric 名解析，例如 `es_hs_99` → ES 历史模拟、99% |
| `stress_loss:<id>` | 压测页 | 该情景 |
| 其他 | 不出链接 | 写明"没有对应的说明页面" |

2026-09-18 的五条链接：

- L_CONC_INST → 敞口 · 高亮 SZ002475 立讯精密
- L_VAR99 → 归因 · VaR 历史模拟 99%
- L_CONC_IND → 敞口 · 高亮 电子
- L_ES99 → 归因 · ES 历史模拟 99%
- L_STRESS_2015 → 压力测试 · 选中情景 HIST_2015

### 3.2 URL 和控件谁说了算

规则：**URL 带来新值时用 URL 的值；之后以控件为准，控件再写回 URL。**

- `adopt_query_param` 记下每个参数上一次见到的值，只在值变了时（点了链接、粘贴了链接、刷新页面）才把它写进控件状态，所以用户跳转后还能改控件。如果每次重跑都用 URL 的值，用户一改控件就会被改回去，有测试守着这一点。
- `write_query_param` 把控件的当前值写回 URL，所以页面可以原样刷新或分享。
- **用户把控件改离了 URL 带来的值时，丢掉跳转上下文**（`from`、`inst`、`ind`）：改了日期以后，"从 L_CONC_INST 跳来、高亮 SZ002475"已经不是用户在看的东西了。
- 压测页的排名表高亮的是"下钻当前选中的情景"，而不是 URL 里的情景：读的是重跑开始时已经更新的控件状态，所以换情景后高亮不会滞后一次。归因页和压测页的跳转说明放在页顶的占位里，等控件写回 URL 之后再填。
- 侧边栏导航换页时，Streamlit 会清掉页面专用的参数，只保留 app.py 写回的 `date` / `conf`。在浏览器里核对过。
- URL 里的值无效（不在完整日期里的日期、不在配置里的置信度、未知指标）时忽略，用默认值。

## 4. ES 风险贡献

### 4.1 方法

记组合在 T = 250 个历史场景下的损益为 p_t，个股 i 的损益为 x_{i,t}，p_t = Σ_i x_{i,t}。历史模拟 ES 是尾部场景的平均损失：

- 尾部 = {t : p_t < −VaR_hs}，与 `hs_es` 取平均的那些天完全相同；
- ES = −mean_{t ∈ 尾部} p_t；
- **个股贡献 c_i = −mean_{t ∈ 尾部} x_{i,t}**；行业贡献同理，用行业的损益。

因为 p_t 是各股之和、均值是线性的，**Σ_i c_i = ES 精确成立**，行业之和同样成立。这就是 ES 对持仓的 Euler 分解：ES 对持仓是一次齐次的，c_i = e_i · ∂ES/∂e_i。

- **可以为负**：在组合最坏的那几天平均赚钱的股票，对组合 ES 起对冲作用。
- **尾部为空时**（P&L 有并列，或者整个窗口都没动，没有一天严格低于 −VaR）：ES 按引擎的约定等于 VaR，贡献就取 VaR 的 Euler 分量，即插值两天的加权。各分量之和仍等于 ES。
- `risk_result` 里：个股行、行业行存对组合 ES 的贡献；组合行存 ES 本身（直接复制 `es_hs`，所以这一行与 `es_hs` 逐位相等）。同一置信度内，个股行之和、行业行之和都等于组合 ES。

代码：

- `engine/var.py` 的 `hs_var_components`、`hs_es_components`：原来写在 `engine/attribution.py` 的 `risk_components` 里，逐字搬出，归因改为调用它们（§5.2 验证了归因结果逐位不变）。
- `compute_risk` 用组合那一列的损益确定尾部，正是算出已存 ES 的那一列，所以贡献对应的就是库里那个 ES。

### 4.2 尾部有几天

线性插值的分位数位于排序后损益的第 h = (1 − c)(T − 1) 位（从 0 数起）。没有并列时，严格低于它的是第 0 … ⌈h⌉ − 1 位，共 **⌈h⌉ 天**。h 恰好是整数时，分位数就是那一天的损益，它不严格低于自己，所以还是 ⌈h⌉。

| 置信度 | h = (1 − c) × 249 | 尾部天数 |
|---|---|---|
| 99% | 2.49 | **3** |
| 95% | 12.45 | **13** |

- `tests/test_var.py` 在 250 个随机损益上核对过这两个数。
- 看板上的天数按 `lookback_days` 算出（`tf.tail_days`），不是写死的。
- 置信度不是配置里最低的那个时，页面显示提示：

  > 尾部仅约 3 个场景，贡献随单日剧烈变化，建议以 95%（尾部约 13 天）为准。

  页面跟随侧边栏的置信度，不自动改成 95%。

### 4.3 为什么不分解 VaR

历史模拟 VaR 只取决于插值的两个场景日。哪两天落在分位点上，随窗口每天滚动、随持仓权重变化，换来换去，分量也就跟着整体跳。

在 demo 库上用同一套引擎函数算了四种分量（只是算，不入库），看各股贡献占比的日换手（½ Σ_i |Δ 占比_i|），496 个日变化：

| 分量 | 日换手中位数 | 90% 分位 | 最大 | 换手 > 10% 的天数 | > 20% |
|---|---|---|---|---|---|
| VaR 95% | 1.3% | 37.2% | **72.4%** | **159** | 152 |
| VaR 99% | 1.0% | 2.6% | 35.6% | 36 | 16 |
| ES 99% | 0.9% | 2.0% | 22.1% | 6 | 1 |
| ES 95% | 1.0% | 3.3% | 12.6% | 3 | 0 |

- VaR 95% 的分位点落在分布的稠密处，相邻两天的损益接近，插值的那两天频繁换人。所以约三分之一的日子（152 / 496 天）里，组合风险的"来源"会重排两成以上，这是噪声，不是信息。
- ES 把尾部平均掉，换人时一天只占 1/13（95%）或 1/3（99%）的权重。
- 作为对照，市值权重的日换手中位数是 0.9%。ES 贡献在平常日子里的变动与持仓变动同一量级。

### 4.4 99% 的不稳定在哪里

上表的数据显示：99% 的不稳定**不在每一天，而在少数几天**。

- 平常日子里，最坏的 3 天都还在窗口里，贡献只随权重缓慢漂移：中位数 0.9%，与 95% 相近。
- 一旦有尾部场景移出或移入窗口，三分之一的权重一次换掉。日换手超过 10% 的有 6 天，95% 只有 3 天；最大一次 22.1%（2024-10-09），95% 最大 12.6%。
- 所以"建议以 95% 为准"成立，但 99% 的"剧烈变化"是偶发的跳变，不是天天在变。看 99% 的贡献时，要留意窗口两端有没有极端日进出。

### 4.5 2026-09-18（demo 库）的结果

| 行业 | 市值占比 | ES 贡献占比 95% | ES 贡献占比 99% |
|---|---|---|---|
| 电子 | 23.0% | 33.4% | 31.5% |
| 有色金属 | 17.9% | 23.7% | 23.2% |
| 电力设备 | 17.3% | 17.6% | 14.1% |
| 计算机 | 11.4% | 14.9% | 12.7% |
| 食品饮料 | 8.5% | 2.7% | 5.2% |
| 医药生物 | 8.2% | 5.1% | 5.7% |
| 银行 | 7.5% | **−1.1%** | 1.9% |
| 非银金融 | 6.3% | 3.6% | 5.7% |

- 电子、有色金属两个行业合计占市值 41%，在 95% 下贡献了 57% 的 ES：组合最坏的日子主要亏在它们身上。
- **银行在 95% 下是负贡献**：组合最坏的 13 天里，银行股平均是赚钱的。这与压测页"银行 −10%（β 传导）下组合反而盈利"是同一件事的两面，见 3B 文档 §5.5 b。

  两年里，银行的贡献占比在 95% 下介于 −1.1% 到 5.3% 之间，99% 下介于 −0.6% 到 7.2% 之间；497 天里，有 100 天至少有一个行业在 95% 下是负贡献。

## 5. 旧库升级与"逐位相同"

### 5.1 升级

库是旧版本建的、缺少 `es_hs_contrib` 时：

- **补列**：`init_db` 比对 schema 和库，对缺少的可空、非主键列执行 `ALTER TABLE ... ADD COLUMN`，已有的行得到 NULL。所有会写库的命令都先调 `init_db`，所以打开就补，不用重建库。
- **补算**：`fill_es_contrib` 找出这一列为 NULL 的持仓日，逐日用同样的输入重算 `compute_risk`。**只有当重算出的市值、两种 VaR、ES 与库里已存的逐位相同时，才写这一列**：这样补进去的贡献，正好对应表里现有的那个 ES。不等时，这一天不写，记日志，提示对该日重跑 `mrisk risk`。
  - 只用 UPDATE 写这一列，其余列和 `run_id` 都不动。
  - 已经补过的日期不会再算，所以可以重复运行。
- **`mrisk upgrade-db`**：只做上面两步，有日期没补上时退出码为 2。其他写库的命令也会自动做，补算失败只记日志，不让命令失败。
- **看板和 `diff-db` 只读**，遇到旧库时直接说明要先运行 `mrisk upgrade-db`，不抛 SQL 错误。

### 5.2 在新结构下重新证明逐位相同

| 比对 | 结果 |
|---|---|
| 重构 `risk_components` 前后：在旧 demo 库的副本上用新代码重算 496 天归因，与原库 `diff-db` | `var_attribution` 610,890 行**逐位相同**（`run_id` 已换成新的，确认是重算过的行，不是原行） |
| 旧版本的 demo 库副本 → `mrisk upgrade-db`（497 天全部补上，约 23 秒）→ 与新代码重建的 demo 库 `diff-db` | **17 张表全部逐位相同**，包括新列；`risk_result` 48,706 行 |
| 旧版本的 demo 库直接 `diff-db` | 拒绝比对，提示先 `upgrade-db`（退出码 2） |

推理链：

- 第 4 周 B 已经证明：作者本机的真实库 = 旧 demo 库（逐位）；
- 本轮证明：upgrade(旧 demo 库) = 新 demo 库（逐位）；
- 升级只依赖库内容和代码，所以 upgrade(真实库) 也应等于新 demo 库。

这一步要在作者本机复验，命令：

```sh
uv run mrisk upgrade-db                          # config.yaml -> data/mrisk.db：补列 + 只补算这一列
uv run mrisk demo --overwrite                    # 用新代码重建 data/demo.db（约 2.5 分钟）
uv run mrisk diff-db data/mrisk.db data/demo.db  # 期望 17 张表全部 identical
```

## 7. 已知局限与待定

1. **数据来源取自配置**，库本身不记录（§2）。要可靠，得在库里加一张元数据表，需要改 SPEC。
2. **99% 提示的措辞**：按 §4.4 的数据，99% 的不稳定是偶发的大跳变，平常日子与 95% 相近。提示用的是拍板时定的原文，没有改。
3. **自动补算的时机**：每条写库命令都会检查有没有 NULL 的贡献。一次全量补算约 20 秒；有补不上的日期时，每条命令都会重试并记一次日志，直到对该日重跑 `mrisk risk`。
4. **SPEC 只同步了 §3.6**。§5.2 的计算步骤、§7 的敞口页描述还没提 ES 贡献，要不要补，等拍板。
5. **跳转上下文只在总览出发**：限额页的规则表还没有同样的链接。`limit_target` 是纯函数，接上只需几行。
