# 第 1 周：数据模型 + 数据管道 + mock 持仓 + 12 条 DQ 规则

## 1. 做了什么

```
akshare(新浪源) ──► data/sources.py ──► data/transform.py ──► daily_price
   │  限速/重试/parquet 缓存       后复权·停牌补行·剔除上市前行
   │
   ├─ 申万一级成分 + 交易所列表 ──► data/universe.py ──► instrument
   ├─ seed/code_map.csv ─────────────────────────────► instrument_code_map
   │
mock 上游持仓系统 data/mock_positions.py ──► data/feed/positions_P001.csv（切换日前写旧代码）
                                               │
                           data/code_map.py 解析旧代码 ──► position
                                               │
                         data/dq/（12 条规则，纯函数）──► dq_rule / dq_result（blocking 失败阻断当日）
```

- `db/`：SPEC §3 全部表，外加 `trade_calendar`、`dq_rule`、`dq_result`。SQLAlchemy Core 编写，SQLite 与 PostgreSQL 通用（upsert 按方言分派，JSON 列在 PG 上用 JSONB）。
- `jobs/`：编排层，是唯一同时碰网络、文件和数据库的地方。命令行入口：
  - `mrisk build-universe`：生成股票池 seed
  - `mrisk backfill`：全量回灌
  - `mrisk daily [--date]`：单日增量
  - `mrisk dq --start --end`：重跑 DQ
  - `mrisk schedule`：APScheduler，工作日 16:30（上海时间）

## 3. 北交所 920 号段

- **事实**：北交所存量股票于 2025-10-09 全面切换到 920 代码，规则是"后三位不变"。其中 6 只试点股先于 2025-05-06 切换，例如球冠电缆 834682 → 920682。
- **数据源的行为**：新浪已经把整段历史合并到新代码下（920682 的行情跨过 2025-05-06 是连续的），用旧代码 834682 查询返回空。也就是说，行情这一侧用不到映射表。
- **映射表在哪里起作用**：持仓侧。mock 上游持仓系统在 2025-05-06 之前用旧代码记账（落地到 `data/feed/`），装载时由 `resolve_instrument_id` 映射到同一个 `BJ920682`。
- **解析规则**：
  - 旧代码只在生效日之前有效，生效日当天及之后出现旧代码直接报错；
  - 新代码任何日期都有效（因为数据源已经把历史统一到新代码）；
  - 解析不了的行报错，不会被悄悄丢掉。
- **映射表来源**：`seed/code_map.csv` 是手工维护的参考数据，akshare 没有提供新旧代码对照接口。

## 4. 关键取舍

- **行情源用 akshare 的新浪接口**（`stock_zh_a_daily`）。东方财富接口对本机 IP 直接断开连接（换了浏览器 UA、TLS 伪装都不行），腾讯接口不支持北交所。新浪同时提供原始价和后复权因子，我们自己计算 `adj_close`。
- **绕过代理**：本机设置了 `HTTPS_PROXY=127.0.0.1:7890`，访问国内站点时握手失败。`config.yaml` 里的 `data.bypass_proxy: true` 让拉数时直连。
- **停牌日**：新浪对停牌日不返回行。凡是落在一只股票首个和最后一个有行情日期**之间**的缺失交易日，都补一行：`close` 和 `adj_close` 沿用前值，`volume=0`，`is_suspended=True`；有行情但成交量为 0 的行也标为停牌。首尾的缺口不补，留给 DQ01 报出来（例如当天行情没有拉到）。
  - 已知局限：区间内部的缺口到底是真停牌还是数据源漏数，目前分不清。
- **申万行业**：
  - 按申万一级行业逐个拉指数成分（`index_component_sw`），成分只数与官方的"成份个数"一致；
  - 这批成分**不含北交所股票**。BJ920682 的行业来自 `seed/industry_override.csv`（电力设备，依据见文件备注），**待确认**；
  - 行业补充文件只填申万成分缺失的股票；如果补充的股票申万成分其实已覆盖，就报错，防止过期的补充值覆盖真实数据；
  - 申万官网的全量分类接口因证书链不完整而失败，没有采用关闭证书校验的方式去拿。
- **mock 持仓**：
  - 初始资金 1 亿，40 只股票，每个行业轮流挑选以保证行业分散；单只股票初始权重上限 8%；
  - 每周第一个交易日调仓：随机挑 4 只股票调整数量 ±10%；有 25% 的概率在同行业内换掉一只；
  - 两次调仓之间，持股数量按"后复权因子相对上次调仓的比例"缩放并取整到整手。效果是：送转股会如实增加股数；现金红利因为不足一手的部分被舍掉，等同于不再投资；
  - seed 固定，结果可复现。延长结束日期不会改变已经生成的历史。
- **DQ04 容差**：
  - 平日取 `max(0.1% × 参考价, 0.01 元)`。只用 0.1% 的话，低价股的最小变动单位会造成误报：例如前收 1.05 元，涨停价四舍五入到 1.16 元，涨幅是 10.48%。
  - 除权日（复权因子有变动的那天）放宽为 `max(0.5% × 参考价, 0.01 元)`。原因是用复权因子倒推的参考价只是交易所除权参考价的近似，配股时偏差尤其明显。实例：浪潮信息 2017-07-27 配股复牌，交易所参考价约 15.15，涨停价 16.67；因子倒推的参考价是 15.11，按 0.1% 容差会误报。这个例子已写进手算测试。
- **数值类型**：价格和数量用 `Float`（双精度），不用 `Numeric`，避免 SQLite 里的 Decimal 转换问题；风险计算本来就是浮点运算。
- **持仓表加了约束** `quantity > 0`（只做多头）。`cost_price` 是可选字段，mock 持仓不生成。

## 5. 怎么验证的

- **单元测试**：`uv run pytest`，共 76 个，另有 1 个联网测试默认不跑，用 `-m network` 单独运行。
  - 手算用例：DQ04 共 11 组（主板、ST、创业板新旧涨跌幅、北交所、最小变动单位取整、除权日参考价、浪潮信息配股实例）；后复权计算；DQ11 的市值变化 `85330/42550−1`；DQ12 的行数变化 `−1/3`。
  - 每条 DQ 规则都有"干净数据通过"和"故意弄坏后被抓到"两类用例。
  - 端到端测试：用假数据源跑一遍回灌和一次每日增量。确认：
    - DQ 全部通过；
    - 回灌数据的 DQ10 记为 skip，每日增量的 DQ10 为 pass；
    - 停牌补行正确，包括跨越窗口起点的停牌；
    - 持仓文件在切换日前用旧代码，入库后映射到同一只股票。
- **真实回灌验收**：见 §6。

## 6. 验收结果（真实数据，2026-09-19 运行 `mrisk backfill`）

| SPEC §10 验收项 | 结果 |
|---|---|
| 2 年行情入库 | `daily_price` 共 229,334 行：81 只股票，2015-01-05 至 2026-09-18，其中停牌行 2,735 行。持仓 2024-09-02 至 2026-09-18，共 497 个交易日 × 40 只 = 19,880 行 |
| DQ 全部通过 | 2,848 个交易日 × 12 条规则，**没有任何 fail**。skip 的原因：DQ02、06、07、11 在 2024-09 之前没有持仓可查；DQ10 的回灌数据按设计 skip；DQ04、05、12 在第一天没有前一日数据 |
| 代码映射表处理一只北交所股票 | 持仓文件里 834682 用于 2024-09-02 至 2025-04-30（158 天），920682 用于 2025-05-06 至 2026-09-18（339 天）。入库后全部是 `BJ920682`，股数跨切换日连续（797,700 股） |

其他核对：

- **后复权**：SH600000 自算的 `adj_close` 与新浪自己的后复权序列逐日比较（2,816 天），比值在 0.99996 到 1.00005 之间，对数收益率最大偏差 8.7e-5。偏差来自新浪只保留两位小数。
- **组合**：
  - 每天恰好 40 只股票、8 个行业，两年里累计持有过 59 只；
  - 市值从 1.00 亿到 1.77 亿，最大单日变动 9.3%，DQ11 的 30% 阈值没有触发；
  - 单只股票的最大权重是 11.46%，**超过 SPEC §6.2 的 10% 限额**。这不是数据问题（mock 只限制了初始权重 8%，之后权重会随涨跌漂移），第 3 周的限额监控会把它记为 breach。
- **真实回灌中暴露并修掉的问题**：
  - pandas 3 下日期精度不一致导致合并报错；
  - 窗口起点处于停牌中的股票没有补行（DQ01 连续 13 天失败）；
  - 浪潮信息配股日 DQ04 误报。
  - 三处都补了回归测试。

## 7. 已知局限 / 待确认

1. **BJ920682 的申万行业是手工指定的**（电力设备），需要你确认。
2. **每日模式下，当天停牌的股票无法标记。** 新浪不返回停牌日的行，这一行又处在序列末尾，按设计不补；而东方财富的停复牌接口被封。后果是 DQ01（warn）报缺失；如果这只股票正在持仓中，DQ02（blocking）会阻断当天计算。要解决，需要一个停牌信息来源。
3. ST 状态按当前简称近似。历史上戴过帽、现在已摘帽的股票，当年的 5% 涨跌幅限制无法识别。股票池已排除当前 ST 股，暂时没有影响。
4. 与 SPEC 原文的差异（后复权、DQ10、调度时间、新增表和字段、risk_result 长表）只记录在本文档，**没有改 SPEC.md**。
5. 本机 IP 被东方财富封了，新浪也有限流，所以拉数间隔 1 秒并带重试。申万成分接口很慢（31 个行业约 25 分钟），每日任务不刷新证券主数据，只在回灌时刷新。
